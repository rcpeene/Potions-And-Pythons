===============================================================================
3. EFFECTS AND STATUS SYSTEM
===============================================================================

The general architecture for dynamic effects (potions, switches, spells,
equipment) and for status conditions. This supersedes the earlier
"data-driven equipment effects" draft: equipment is now one trigger family
of the shared system, and the status-source representation debate is settled
(sourced entries, below).

BACKGROUND

- Controller/Switch effects are eval()'d strings authored in World.json; the
  descriptor registry replaces this as the default while keeping string-eval
  as a deliberate escape hatch.
- Creature.equipInHand() calls item.equip(self) when defined; equipArmor() and
  unequip() call the hooks without the wearer; Armor defines empty hooks. The
  equip-family triggers replace these ad hoc hooks.
- The carrying planner (Heft) already replans after unequipping because
  equipment may alter STR/BRDN; no current item does, so that branch is
  unreachable until Phase D converts one (see DEFERRED CARRYING TEST).

EFFECT SYSTEM DOCTRINE

- Two layers. Layer 1: a registry mapping string names -> functions, built by
  filtering the Effects module's own globals (any function defined in
  Effects.py is referenceable by name; imports/helpers from other modules are
  excluded). Layer 2: the functions themselves, in two kinds: parametric
  primitives (heal, damage, bindStatus, impartStatus, removeStatus,
  areaDamage, areaStatus/areaCreatureStatus/areaItemStatus, openDoor,
  unlockTarget, spawnObject, destroyObject...) shared
  by potions, switches, spells, and equipment alike; and bespoke one-off
  functions (e.g. summonBonesMalone) which register the same way and serve
  as the escape hatch for anything too weird to parameterize.
- A descriptor is a function call stored as data: a tuple of
  (effectName, *descriptorArgs). Not code; serializable; authorable in
  World.json, Material fields, and save files; resolved at fire time.
- Call anatomy: effects[name](actor, source, target, *descriptorArgs). Every
  effect function takes the SAME three-arg context prefix, so one primitive
  serves every trigger family: actor = who is responsible (attribution,
  messaging, curse interactions), source = the object carrying the effect,
  target = what the effect acts on. Dispatchers fill the target slot only
  when the interaction inherently produces a target (consuming has a
  consumer even when force-fed; casting has a chosen victim); flipping,
  opening, and breaking act on no one, so those triggers pass None and the
  primitives' fallbacks decide. Family mapping:
    consume -> (consumer, material object, consumer)
    drench -> (pourer/thrower, fluid, drenched object)
    touch -> (toucher, touched object, toucher)
    ignite/impact -> (igniter/striker or None, material object, victim or
      None; the dispatcher passes the vessel's parent as target-as-area)
    expose -> (opener/spiller or None, material object, None)
    onBreak -> (breaker or None, broken object, None)
    switches -> (triggerer, switch, None; switch targets are authored
      descriptor args)
    spells -> (caster, wand/scroll/None, chosen target)
    equip/unequip -> (wearer, item, wearer); obtain/drop -> (holder, item,
      holder); carry/uncarry -> (carrier, creature, carrier); slot is
      conveyed by qualified trigger keys, not context
  Target resolution inside every primitive is one ordered chain: an authored
  ref wins (if it resolves to nothing the effect fizzles rather than
  redirecting onto someone the author never named), else the runtime target,
  else the primitive's own fallback -- creature effects fall back to the
  actor (a bare ('damage','s',5) on a trap lever shocks the flipper), area
  effects to source.parent (('explode',) on a lever blasts lever.parent with
  force volatility * weight or an authored override), room effects to
  source.room(), and mechanism effects (openTarget) fizzle, having no sane
  default. A primitive grows its ref arg when an authored chokepoint first
  needs it, not speculatively; trailing defaults keep that backward
  compatible.
- Object-ref resolution happens INSIDE effect functions, not in the executor:
  only the function knows which of its params are refs (in ('unlockLock',15,10)
  the 15 is a door and the 10 is a force -- indistinguishable to the caller).
  Ref params pass through a tolerant helper resolveObj(x): a game object
  passes through unchanged, an int id is looked up in game.itemRegistry, and
  a missing id yields None (the effect fizzles gracefully). Direct callers
  that already hold the object just pass it; descriptor data authors ids.
- Spell functions follow the same (actor, source, target, *args) anatomy as
  every registry function, so authored descriptors can route to them too (an
  enchanted lever with ("alohamora", 15)). The Cast verb is simply a direct
  caller that invokes the spell by name with runtime arguments (the chosen
  target in the target slot, the computed casting bonus -- values that cannot
  be authored into static descriptors). Spell-ness is which list Cast
  consults, not a different calling convention.
- evokeEffects(descriptors, actor, source, target=None) is the data->call
  bridge, used only when executing authored descriptor data: it looks up
  each name in the registry, splices in (actor, source, target), branches
  tuple-vs-string (the eval hatch), errors on unknown names, and iterates
  the list; status-hook dispatch (evokeStatusHooks) routes through it, so
  cascades fire inside the mutating call's statusCascade window. Code already
  holding a function reference calls it directly and never needs the bridge.
- Dispatch by descriptor type: a tuple is dispatched through the registry,
  and an unknown name or bad arity is an ERROR (validated at import/load
  where possible), never a fallback. A string descriptor is eval()'d -- the
  deliberate, visibly-exceptional escape hatch for custom situations, and
  what existing Controller/Switch effect strings already are.
- Authoring grammar is ONE descriptor grammar, discriminated by shape alone.
  A descriptor collection is a sequence whose elements are each a
  (name, *args) sequence or a lone string, which is a zero-arg descriptor
  ("explode" means ("explode",)). Coded data (Data.py materials and
  conditions) writes CANONICAL tuple-of-tuples only; __post_init__ asserts
  rather than repairs, so bare authoring fails at import. The flexible
  grammar is a boundary-parsing concern owned by
  Effects.wrapEffectDescriptors, applied where authored data enters from
  outside Python (Item effects load, evokeEffects): lists and tuples are
  interchangeable there (JSON only has lists) and cast to canonical
  tuple-of-tuples. There is NO single-descriptor shorthand:
  one descriptor with args is authored (("bindStatus","x"),) -- a bare
  ("bindStatus","x") parses as two zero-arg descriptors and fails name
  validation loudly at load. The escape hatch: an authored value that is a
  bare string (the WHOLE value, never an element) is exec'd as code, so
  multi-statement hatches work; the shape survives JSON unambiguously
  because a string INSIDE a collection is always an effect name. Coded
  data (materials, conditions) does not allow eval values at all; the
  hatch exists only for world-authored data (Item effects,
  Controller/Switch strings).
- Descriptor args that reference game objects are authored as object IDs and
  resolved at fire time inside the effect function via resolveObj (never
  bound at load). A missing ID means the effect fizzles gracefully.
- Material carries seven trigger fields holding descriptor tuples (pure data,
  so they live in Data.py without import concerns), validated at import time
  against the registry [IMPLEMENTED]:
    consume   eaten or drunk (unifies drinking fluids and eating food)
    drench    applied/splashed onto the target, EXPENDING the material
              (pour, splash, immersion; dose consumed)
    touch     contacted by the target; the material persists (grabbing lava,
              stepping in acid, seizing a lightning bolt)
    ignite    received any fire damage (fires iff descriptors exist; no
              volatility gate -- oil catches, wood will burn, black potion
              explodes)
    impact    received a single blunt hit at or past the volatility
              threshold (volatility's ONLY job now); different substances may
              respond differently to ignite vs impact
    expose    unsealed to open air (see below)
    onBreak   broken/destroyed: EXTRA authored consequences (soul crystal
              frees its ghost); the shatterable flag separately routes HOW
              the object physically breaks. Field/flag doctrine: fields and
              flags are for engine-queried state and control-flow routing;
              descriptors are for authored consequences of discrete events.
  Chokepoints fire material triggers by direct field access on the record --
  evokeEffects(obj.material().ignite, actor, obj, area) -- read at call time
  (no dispatcher wrapper: every chokepoint knows its trigger statically, and
  a triggerMaterial(trigger,...) indirection was cut as premature).
  Material.igniteThreshold() and
  .impactThreshold() derive the stimulus thresholds (see the volatility bands
  in section 4). consume/drench/touch/ignite/impact chokepoints are wired
  in later phases; the fields exist now so the schema is settled.
- Item gains one optional effects dict keyed by trigger name whose values are
  descriptor lists. Trigger vocabulary: "obtain"/"drop" (inventory),
  "equip"/"unequip" (any slot), slot-qualified "equip:head" etc.,
  "equip:grip" matching any grip slot, "carry"/"uncarry" (carried
  Creatures -- Creature extends Item, so a carried imp can grant effects),
  "open"/"close" (fired from the Box.open/close chokepoints), and the
  lifecycle keys "spawn"/"destroy" (next bullet). open/close/spawn/destroy
  are instantaneous events, not binding arrival/departure pairs, so no
  derived inverses.
  Creature.remove already calls the I.Drop hook, which is the chokepoint for
  drop triggers. Content note: "lightning in a bottle" = a floating Item
  (composition "lightning", flying status, weight 1), NOT a plash -- liquid
  machinery (drinking, mixing, puddles, pouring) is all wrong for a captured
  bolt. Its Material carries expose/impact/touch descriptors; the authored
  bottle needs no instance effects at all.
- The "expose" trigger: descriptors fired when an
  object of that material stops being sealed away. Two chokepoints: opening a
  vessel fires expose for EVERY content object's material (contents-general,
  not fluid-specific, so bottled items and plashes behave alike), and
  Room.add (where timeDespawn/mention flipping already live) fires expose for
  arriving objects whose material has expose descriptors -- so smashing,
  pouring out, and decanting all count as exposure with no special casing.
  Volatility remains the separate direct-damage route. Lightning:
  expose=(("explode","l",20),). Generalizes to bottled fog, vacuum,
  sealed screams, etc. Exposure does not fire on consume (a drinkable
  volatile authors its consume consequences explicitly).
- LIFECYCLE TRIGGERS "spawn" and "destroy": instance-level authored
  consequences of entering or leaving the world. These add no cleanup
  responsibility (the no-posthumous-cleanup rule below is untouched); they
  exist because lifecycle moments can carry authored consequences like any
  other discrete event.
  "spawn" fires from Game.spawn ONLY -- the gameplay chokepoint -- after
  registration and parent attachment succeed, with context
  (spawner-or-None, object, None). World construction and save loading
  never fire it (they do not route through gameplay mutation APIs), so
  loading a save replays nothing; timed room spawning routes through
  Game.spawn and correctly does fire. Canonical use: a creature that
  manifests in a blinding blaze authors
  spawn=(("areaCreatureStatus","blinded",20),) -- the area primitive's
  source.parent fallback is exactly "everyone present where it appeared".
  "destroy" fires inside Item.destroy AFTER the forced unbinding
  operations (unequip/drop/uncarry/off keep doing all status stripping
  via derived inverses, ordered first) and BEFORE removal from parent, so
  source.parent still resolves for area effects. Context is
  (destroyer-or-None, object, None). Canonical use: plot-critical
  destruction -- the evil orb authors a descriptor that records a world
  event when it is truly destroyed. destroy() MEANS destroy: every path
  through it fires the trigger -- combat, explosions, scripts, despawn,
  and replace()'s succession mode alike; there is NO suppression rule
  (see REPLACEMENT MODES below; an earlier suppression ruling was
  repealed as needless machinery). Breaking is NOT replacement: breaks()
  calls destroy() directly and shatter() spawns NEW Shard objects with
  fresh ids, so breaking/shattering DOES fire the destroy trigger. An
  author whose plot item must distinguish "properly destroyed" from
  merely broken makes it unbreakable (durability -1 refuses breaks and
  shatter), leaving scripted destruction as the only exit, or gates
  inside a bespoke descriptor function.
  Conditions narrower than "any true destruction" (the orb only counts
  when cast into the volcano) are bespoke registry functions gating inside
  themselves, per the escape-hatch doctrine. onBreak remains the MATERIAL
  home for every-object-of-this-substance breakage consequences; the
  destroy key is for this one instance. D5b's purgeSourced is authored on
  this key. Open question: destroy() is also reachable through despawn
  timers and displace()'s overflow fallback; see CAVEATS.
- Automatic symmetric removal by DERIVED INVERSES: authors do not write
  removal descriptors for status grants. The knowledge of what to remove
  lives in the item's own authored effects dict: each departure trigger
  mirrors its arrival trigger (unequip <- equip, unequip:head <- equip:head
  via the slot in context, drop <- obtain, uncarry <- carry) and derives
  inverse descriptors from the authored arrival list, in reverse order.
  bindStatus(name,dur) derives removeStatus(name, source=item.id), which
  removes ALL entries matching the criteria, consistent with existing
  removeStatus semantics (duplicate derivations from stacked grants are
  harmless no-ops). Derivation is (statusName + source)-scoped, never a
  source-blanket strip, so a sword granting +1 STR on obtain and brawniness
  on equip keeps its obtain grant through an unequip. Authoring rule: do not
  grant the SAME status name at multiple tiers of one item (the entries are
  indistinguishable and one tier's departure would strip both); use distinct
  names or author that tier's departure manually. Over-removing a conditional
  grant that never fired is a harmless no-op. Only invertible primitives
  derive inverses (bindStatus); mutations and bespoke functions derive
  nothing and need authored reversal.
  impartStatus derives nothing by design (lingering effects, source left
  None/authored). There is NO posthumous cleanup: destroy() does no status
  work itself; it forces the unbinding operations (unequip, drop, uncarry,
  off) on its way out, and those departures do all stripping via derived
  inverses. An unheld object destroys with zero cleanup (its bound statuses
  were necessarily stripped at its last departure). nullify() keeps its
  explicit blanket removeStatus(source=id) strip as its stated job.
- Departure-trigger authoring convention: a departure key (drop/unequip/
  uncarry) that is absent or None means automatic behavior (derived inverses
  run). An explicitly empty tuple () SUPPRESSES derivation for that tier, so
  its grants linger after departure (cursed-ring case). A key with authored
  descriptors REPLACES the derivation (the author takes manual control).
- Changing an item's effects dict at runtime (disenchantment) is itself a
  departure moment: strip/derive from the OLD dict first, then apply the new
  dict's arrival triggers if still equipped/held; otherwise the eventual
  unequip would mirror the new list and orphan old grants. Same risk applies
  to editing authored content between a save and a load; recoverable via
  generic removal since sourced entries never resist generic dispels.
- Equip context tuple is (wearer, item, slot). Slot changes are always a full
  unequip+equip cycle, never a silent reslot. Reslotting paths that must each
  fire triggers exactly once per ITEM (not per occupied slot):
  equipInHand (multi-grip items), unequip (clearing several slots),
  checkGrips auto-correction, Heft carry replanning, and death/destroy/theft/
  drop of an equipped item (unequip triggers fire before obtain/drop ones).
- Normalization boundary: derived-state checks (checkGrips, checkHindered,
  carry replanning) never run inside an effect batch. Run the batch to
  completion, then run checks once; forced corrections discovered by a check
  fire their own batch, then one more check pass, until stable. Termination
  is guaranteed by monotonicity, not by effect contents: automatic
  correction only ever UNEQUIPS, never equips, so each pass shrinks the
  equipped set or reaches stability (paradox items -- wieldable only while
  not wielded -- settle to the consistent off state). Authoring rule:
  unequip effects must not themselves equip; if ever enforced, reuse the
  cascade-guard pattern (an embargo set per normalization episode).
- Object IDs are safe to use in descriptors and sources because they are
  permanently unique: game.nextObjId persists in the save, so a destroyed
  object's ID is never reissued. Monotonic growth is harmless
  (arbitrary-precision ints, native JSON, dict lookup).


SOURCED STATUS ENTRIES (replaces the negative duration source codes)

- Status entries are [name, source, duration] (source before duration:
  it is the more significant and less often defaulted field). Durations are
  purely temporal: a positive int = timed, None = indefinite. Negative
  durations are stale data and fail loudly at normalization.
- source is one of:
    None            generic; matches/removable by anything (most statuses)
    int             a specific object's ID (two-swords fix; which liquid
                    wets you); resolved via game.itemRegistry only on need;
                    serializes natively
    str             a symbolic cause code, UPPERCASE_WITH_UNDERSCORES for
                    flavor: "AREA" (maintained by present location, the old
                    -3), "PERMANENT" (removable by nothing, the old -1),
                    and named causes replacing the old per-status constants:
                    HINDERED_INVENTORY/STICKY/CARGO -> "INVENTORY"/"STICKY"/
                    "CARGO", COZY_BED/FIRE -> "BED"/"FIRE", RESTRAINT_CARRY/
                    BINDINGS -> "CARRY"/"BINDINGS", HIDDEN_COVER/CONTAINER ->
                    "COVER"/"CONTAINER"; wetness and submersion are sourced
                    "IMMERSED" (in liquid) or "SUBMERGED" (fully under),
                    re-sourced by submerged's own transfer hooks as
                    submersion changes.
- countStatus/hasStatus/removeStatus filter on all three axes (name, source,
  duration). "*" is the wildcard and the signature default on every axis;
  any other scalar is an exact match, so source=None matches only UNSOURCED
  entries and duration=None only INDEFINITE ones (name may also be a
  collection, matching any member). The one exclusion: with the source axis
  left at "*", "PERMANENT"-sourced entries are skipped -- they are only
  touched by an explicit reqSource="PERMANENT". removeStatus removes ALL
  entries matching the criteria. The entry's source records its
  ORIGIN: every family injects source = the carrying object's id when it has
  one (bound and imparted alike; None only when there is no
  identifiable carrier). A dead-id source is legal, permanent attribution --
  ids are never reused (nextObjId is persisted), so it can only point at
  nothing, never at the
  wrong thing; there is no dangling-ID backstop and no scanning cleanup.
  Whether a grant is MAINTAINED is not a property of the entry but of the
  trigger family that granted it: binding families author arrival lists, so
  their grants get departure-stripped by derived inverses; instantaneous
  families (consume/drench/touch/ignite/impact/expose/onBreak, spells,
  switches' instantaneous triggers) leave no arrival record, so their grants
  ride their own timers and outlive their granter (a drunk potion's
  swiftness persists, attributed to the consumed plash's dead id). Because
  generic removal matches any source, sourced entries are protected from
  OTHER sources' targeted removals, never from generic dispels/timeouts --
  an orphaned sourced condition (from a missed-chokepoint bug) is always
  cleanly removable, though with no backstop it persists until something
  removes it (smoke tests pinned the chokepoints instead). The call-slot source
  converts to the entry source via Effects.originId: None and str/int codes
  pass through verbatim, a game object contributes its .id (and an id-less
  object in the slot is a loud dispatch bug, not a silent None).
- Entry model invariants: (name, source) IS an entry's identity -- at most
  one entry exists per pair. Re-adding an existing pair REFRESHES its
  duration (never shortens: max, with None as the longest) and fires no
  hooks or reports; addStatus returns True only when state actually
  changed. stackable=False (or allowStack=False at the call site) freezes
  the duration instead of refreshing (anti-stunlock). addStatus asserts
  durations are None or positive. self.status keeps a canonical order
  (statusEntryKey): name alphabetical, same-name ties longest-first with
  indefinite first.
- Stacking: presence and count are two queries over the same entries.
  Presence conditions (brawniness) are read via hasStatus -- multiple
  sources maintain presence, effect constant. Counted bonuses (+1 CON gear)
  are read via countStatus -- the bonus IS the entry count; a +2 item grants
  two entries under its own source; removeStatus(source=id) strips its whole
  contribution. Two StatusCondition fields govern this:
  stackable=True (may a new entry be added while the condition is present?
  False refuses any-source adds, only for conditions where a second binding
  can never matter) and compounds=False (does countStatus count or cap at
  1?). bindStatus refusing a duplicate from the SAME source is a separate
  structural idempotence layer, independent of both fields.
- transferStatus(name, source, newSource, newDur="*") is CUSTODY TRANSFER:
  same condition, new maintenance terms, no state transition. It edits the
  matching entry IN PLACE -- no hooks, gates, or reports fire in either
  direction; it is entry surgery, not an event, the semantics an inlined
  remove+add can never express (real transitions go through addStatus and
  removeStatus). (name, source) is an exact match-spec (an explicitly named
  PERMANENT entry IS transferable); newDur "*" keeps the old duration, None
  sets indefinite, and unlike refresh a transfer MAY shorten. If an entry
  already exists under newSource, the two merge by refresh rules (frozen
  for unstackable conditions). Canonical use: unimmersion transfers wet
  from maintained (source "IMMERSED"/"SUBMERGED", duration None) to a
  drying clock (unsourced, 21); submerged's own hooks re-source wet between
  IMMERSED and SUBMERGED.
- Death and destruction strip through the unbinding operations, never
  posthumously: a dying creature's carried/equipped relationships fire their
  departure triggers (so a corpse grants nothing); a destroyed item fires
  unequip-then-drop (or "off" for an ON switch) on its way out. Trigger
  dispatchers do not fire for dead sources.
- Maintained area effects chain two levels of the same machinery: a Switch's
  "on" trigger grants the ROOM a condition via addRoomStatus (bound,
  source = switch id; removeRoomStatus is its mirrored departure under "off",
  and destroying an ON switch fires off), while the room condition maintains
  occupant conditions with source "AREA" (granted on entry, stripped on exit,
  re-derived by the status check pass when the room's own status set changes
  -- the status-check machinery). addRoomStatus puts ONE entry on the room itself
  (target if a Room, else source.parent) -- membership semantics; areaStatus
  stamps each current occupant with an independent entry -- snapshot
  semantics. Smashing a lever of maintained darkness thus cascades: off
  strips the room's lever-sourced darkness; the next occupant check strips
  every AREA-sourced darkness it no longer justifies. Fire-and-forget levers
  (pull -> instantaneous areaStatus) remain authorable; the author picks
  semantics by picking the trigger pair.


STATUS REGISTRY AND CASCADES (the materials pattern again)

- Data holds a StatusCondition dataclass registry keyed by status name.
  Fields:
    damage    (factor, dmgtype) tick damage, or None   [was conditionDmg]
    prefix    "curse of" / "blessing of" / None; classifies the condition
              for class-targeted effects (a "remove curse" strips by
              prefix == "curse of", parallel to magical for dispel) and
              derives the default gain/loss messages. Its old third job --
              triggering addStatus's extra checkStatus call -- re-keyed to
              modifies being nonempty          [was curses/blessings]
    color     display color code: "g" / "r" / None=white, used by status
              reports and the stats panel     [was buffs|blessings vs
                                               debuffs|curses membership]
    magical   bool, default False; the target class of dispel-type effects
    gainMsg   bearer-facing report strings; derived at init when not
    lossMsg   authored: "You are X." / "You are no longer X.", or with a
              prefix "You have the curse of X." / "You no longer have the
              curse of X."; authored overrides win. Observer phrasing stays
              reportStatusChange's job
    modifies  dict of trait-name -> int summed into stat getters while the
              condition is present ({"STR":10}), multiplied by entry count
              for compounding conditions; replaces the hardcoded
              conditionalMod pair tables in the ten stat getters
    public    bool, default False; other creatures' instances of this
              condition are reported/shown to you  [was privateStatus,
                                                    inverted]
    displayable bool, default True; shown in the bearer's stats panel and
              the 'status' command output (stat-stick conditions like an
              anonymous "+1 STR" author False to avoid panel clutter)
    immobile  bool; prevents movement/actions         [was immobileStatus]
    stackable bool, default True; may a new entry be added while the
              condition is already present? False refuses the add (returns
              False; only for conditions where a second binding can never
              matter, e.g. dead)
    compounds bool, default False; does countStatus count entries (numeric
              buffs like +1 CON gear) or cap at 1 (presence conditions)?
              moot when stackable=False
    blocks    tuple of condition names this condition vetoes being ADDED
              while present (blocker-declares; checked by
              GameObject.blocksStatus before the stackable gates)
    onAdd     tuple of effect descriptors run through the shared executor,
              fired on EVERY successful add (event-shaped: each splash is
              real)
    onGain    tuple of effect descriptors fired only on the 0->1 transition
              (state-entry-shaped: safely cumulative without guards, e.g.
              freeze-shock damage on becoming frozen)
    onRemove  tuple of effect descriptors fired once per entry removed
              (event-shaped; rare)
    onLoss    tuple of effect descriptors fired only on the 1->0 transition
              (state-exit-shaped: smoldering when the fire is actually out,
              "you are freed" when the last restraint goes)
    onTick    tuple of effect descriptors fired once per present name each
              passTime tick (damage stays its own field: its halfRoll-vs-LCK
              math is engine physics, not authored consequence)
    onExpire  tuple of effect descriptors fired when an entry TIMES OUT --
              the one remove-path with a knowable why; expiry DISPLACES
              onLoss (exactly one of the two fires at a presence-0 moment).
              Canonical use: asleep's onExpire awakens well-rested, its
              onLoss awakens groggy
    onBlock   tuple of effect descriptors fired on the BLOCKER when its
              blocks veto refuses an add (the depleting-ward pattern: wet's
              onBlock dries unsourced wetness, frozen's removes itself, so
              each failed ignition burns off one layer of protection).
              AUTHORING CAUTION: blocks is meant for EVENT-granted
              conditions (burning, poisoned, cursed); check-maintained
              conditions (hindered, hidden, submerged) retry on every check
              pass, so a flat block fights them harmlessly but an
              onBlock-depleting ward would burn a stack per pass and
              evaporate
  (e.g. "wet": onGain=(("removeStatus","burning"),),
   onAdd=(("removeStatus","asleep"),) )
- Cascade engine: hooks fire through evokeStatusHooks INSIDE the mutating
  call's per-object statusCascade window (a depth counter plus an
  alreadyRemoved set of (name, source) pairs, opened by addStatus,
  removeStatus, and flushStatusChecks; nesting shares the outermost
  window). Termination needs no shared action log: a condition removed
  during a window may not be re-added within it (the embargo is checked
  before the blocks gate, so embargoed re-adds fire no onBlock), and
  add-cycles die because a re-add of an existing (name, source) is a
  silent refresh that fires nothing. Reports queue through
  game.deferStatusReports across the whole window, so only NET transitions
  narrate (a condition stripped by its own arrival cascade nets to
  silence) and they print after hooks settle (a splash wakes the sleeper
  before "You are wet." prints). Per-object guards let area cascades react
  on each victim independently.

EFFECTS & STATUS IMPLEMENTATION SEQUENCE

    chokepoints run derived inverse descriptors (mirrored from the arrival
    list, reversed), honoring the None/()
    convention and the authored-replacement rule.
D2b. spawn/destroy lifecycle triggers: spawn fired from Game.spawn only;
    destroy fired in Item.destroy after the forced unbinding operations and
    before parent removal, suppressed by replace(). Pin the replace
    suppression with a test early (replaceID transfers the old ID, so the
    distinction is easy to get silently wrong).
D3. equip/unequip triggers with (wearer, item, slot) context, qualified keys
    (equip:head, equip:grip, carry/uncarry), fired exactly once per ITEM
    across all five reslotting paths (equipInHand multi-grip, multi-slot
    unequip, checkGrips correction, Heft replanning, death/destroy/drop of
    equipped items; unequip fires before drop).
D4. Convert one real item end-to-end (the brawniness example under EQUIPMENT NOTES) and
    re-enable the deferred testCarrying replanning scenario.
D5. Item.nullify(duration=None): strips all statuses sourced to self.id from
    the holder and suppresses the item's arrival triggers -- permanently when
    no duration is given, else until the timer expires. Implemented as a
    "nullified" STATUS CONDITION on the item itself (not a bespoke timer
    attribute): passTime's ordinary decrement ages it, duration None is the
    permanent form, the entry is sourced to the nullifier (so a targeted
    dispel can lift a specific suppression, and source "PERMANENT" makes it
    unliftable), overlapping nullifications coexist as entries with
    suppression holding until the LAST expires, and the re-fire of arrival
    triggers on expiry is simply the nullified condition's 1->0 moment (the
    net-transition machinery). Trigger dispatchers consult
    hasStatus("nullified"); the authored effects dict is never mutated,
    staying serialization-friendly and restorable.
    (Naming note: "disenchant" is the flavorful alternative; nullify is kept
    because not every effect item is magical.)
D5b. purgeSourced effect primitive: removes status entries of a given name
    (or all) sourced to the carrying object's id from every bearer,
    world-wide -- nullify's widened cousin (share the core). Exists for
    standing REMOTE grants whose beneficiaries hold no tether to the source:
    e.g. a button whose press imparts ("impartStatus","sagacity",10) --
    presses accumulate, each on its own clock -- but whose destruction should
    end every outstanding bonus: authored ("purgeSourced","sagacity") on its
    "destroy" trigger key (see LIFECYCLE TRIGGERS). Doctrine note: this does
    NOT reintroduce the deleted
    dangling-id backstop -- the scan is authored, opt-in, and fires once at a
    chokepoint event, never automatically. The termination-at-death toolkit
    by beneficiary location: held/worn -> bound grant + derived inverse
    (automatic); in the source's room -> addRoomStatus chain + off at
    destruction (automatic); scattered anywhere -> impart + authored
    purgeSourced (opt-in).
    FUTURE OPTION (add when purgeSourced lands, if a case arises): a
    purgeEffects flag on replace() and/or destroy() that purges entries
    sourced to the object's id BEFORE retirement. For replace this lets an
    author disown attribution custody: succession transfers the ID, so
    without a purge the successor silently becomes custodian of grants it
    never cast (cursed blade transmuted to holy sword still answers for the
    curse); purging first, while the id still means the old object, severs
    that cleanly. Until then the composed form works: author the purge
    descriptor before the replacement. Suspended objects stay targetable by
    design (a suspended object still resolves in the registry, so
    id-targeted effects act on the latent object and persist into revival);
    purgeEffects is the opt-out for attribution, not a change to
    targetability.
D6. Optional cleanup: migrate Controller/Switch eval strings to descriptor
    lists where they fit primitives (strings keep working as the escape
    hatch regardless).

EQUIPMENT NOTES (retained from the earlier draft)

- Passive semantics: bindStatus under an equip-family trigger injects
  source = item.id; the departure strip removes exactly this item's grants
  while other sources' copies survive. Stat formulas already derive bonuses
  from statuses (Creature.STR() checks brawniness), so no base-trait mutation.
- Direct mutations (creature.str += 5 style) remain possible as bespoke
  registry functions but are discouraged; sourced statuses are the default.
  If a mutation is not trivially reversible, it needs its own undo bookkeeping.
- Module dependency: the import direction is deliberate. Core is engine,
  Effects is content; content names the engine (Core.game, Core.Print,
  Creatures classes for summons), so Effects imports Core and never the
  reverse. The registry is the dependency inversion: engine code invokes
  content BY NAME through the table, not by import. The only bridge needed is
  a local runtime import of Effects inside Core's few dispatch chokepoints
  (addStatus cascades, trigger points), which runs only during gameplay after
  module initialization. (Precedent: Items and Effects already import each
  other lazily without issue.)
- Staged loading: persist authored descriptors on the Item; never persist
  derived passive statuses as independent truth. On load: instantiate,
  resolve gear, validate descriptors against the registry, determine what is
  equipped, reconstruct sourced statuses once, normalize carrying/grips/
  burden, validate silently.

SETTLED AUTHORING RULES

- Non-stacking vs stacking bonuses: presence conditions (brawniness) read via
  hasStatus; counted conditions (+1 CON per gear piece) read via countStatus,
  where the bonus is the entry count and a +2 item grants two entries under
  its own source. Governed by StatusCondition.compounds (entries coexist
  either way; see the stackable/compounds split in the registry doctrine).
- Undo ordering is the author's responsibility: list removal descriptors in
  reverse application order when ordering matters.
- Equipping succeeds even when an effect descriptor fails to apply: the slot
  assignment persists, the failure is reported/logged, remaining descriptors
  still run.
- Statuses supplied by equipment display identically to any other status.
- Object replacement (item.replace) and destruction strip runtime grants
  sourced to the old ID (the death rule); authored descriptors transfer with
  the replacement object as data.

CAVEATS AND OPEN QUESTIONS

- Whether a gameplay rule should CAP stacking for specific counted conditions
  (source tracking preserves every contributor either way).
- Plot-critical destruction vs physics-accident destruction (despawn timers
  and displace()'s fallback reach destroy() too): tracked in PoPy.py's TODO
  list under FUTURE IMPROVEMENTS.
- Known issues in the replacement/suspension machinery (replace/restore/
  destroy/detach/displace), found in review and pending resolution:
  1. [RESOLVED] Succession-replacing a Room permanent crashed in replaceID.
     Fixed: destroy() now returns True on destruction / False on refusal
     (its documented contract), and replace() refuses permanents up front,
     before newObj is ever spawned.
  2. [RESOLVED] The latent-conservation hole is closed by abort semantics:
     if the replacement cannot exist anywhere (placement failed and
     displaceDestination -- the extracted non-mutating planning walk of
     displace -- finds nothing up the ancestor chain), replace() destroys
     the unviable replacement and returns None with the original untouched
     in its exact spot. Room.replaceObj's failure path now re-adds oldObj
     (a failed replacement must leave it where it was). Both modes are
     covered; a replacement that dies mid-handover after successful
     placement remains committed per the succession/fizzle rules.
  3. [RESOLVED] Return types made coherent across the family: destroy()
     returns True on destruction / False on refusal; restore() and
     replace() return the restored/replacement object if it exists in the
     world afterward, else None -- judged by registry state at the end,
     never by which path ran.
  4. [RULED] Latent stasis is by design: nothing reaches a parentless
     object's passTime, so a latent's timers (status durations, hunger,
     despawn, regen) all freeze -- correctly, since every timed consequence
     needs a world to happen in. The suspension clock, if any, belongs on
     the SUBSTITUTE (its expiry/removal drives restore). A duration on the
     latent-side suspended entry is inert -- nothing reads it and nothing
     ticks it -- so it is tolerated, not validated against; authors should
     just know it does nothing.
  5. [RESOLVED] validateWorld now cross-checks the two custody records in
     both directions: every latent bears the suspended status sourced to
     its substitute, and every suspended-status bearer is some
     substitute's .suspended.

SETTLED DESIGN DECISIONS

- Material registry (IMPLEMENTED): Data.Material is a frozen kw_only dataclass
  flyweight; Data.materials maps each material name to its single shared record
  (density, liquid, transparent, shatterable, volatility, taste, scent,
  texture). Game objects store only their composition string (which is what
  serializes and what World.json authors); the record is looked up at call time
  via GameObject.material() or Data.Material.get(name), so composition changes
  from mixing/brewing always re-resolve and nothing non-serializable is stored.
  materials[None] and unregistered lookups resolve to ylem, the formless
  default material (DEFAULT_MATERIAL). GameObject.validate() rejects any object
  whose composition is not registered, at world load and at Game.spawn.
  Senses: Material.__post_init__ derives a missing taste/scent from the other
  via Data.smellToTaste/tasteToSmell and fills nondescript defaults (liquids
  feel wet). Items carry optional per-instance flavor/scent/texture overrides,
  resolved by Item.Flavor()/Scent()/Texture() getters with the same
  cross-derivation (instance > derived > material). The legacy dicts
  (liquids, densities, tastes, scents, textures, transparent, shatterable,
  volatilities) were deleted and all call sites migrated.
  Future material-keyed features should be new Material fields, not new dicts.

- Composite model: a potion is a Bottle (a small glass Box) containing a real
  Plash of a potion-composition fluid. Potion-ness lives in the fluid's
  composition string, not in the vessel class. The old Potion class (hardcoded
  heal-1000 imbibe, phantom drench call in pour) gets deleted.
- "Potion" is the umbrella term for any effectful liquid; coffee and oil carry
  material trigger effects even though they are not literal potions.
- Casks, cauldrons, and other bulk vessels remain plain Boxes. Dose quantization
  applies only at the Bottle boundary; bulk vessels stay continuous-weight.
- Effects: potions are one trigger family of the general effect/status
  architecture in section 3 (see the seven-trigger Material table there:
  consume/drench/touch/ignite/impact/expose/onBreak, fired by direct field
  access through evokeEffects, and the volatility threshold methods).
- Volatility (Material.volatility, 0-10) is one reactivity ladder in three
  bands, read through Material.igniteThreshold()/impactThreshold() (methods
  on the dataclass; None = impossible):
  - 0 inert: cannot burn or react, ever (stone, water, ylem)
  - 1-5 flammable: a single fire hit of 25 - 5*vol damage fires ignite
    effects (1 -> 20, 2 -> 15, 3 -> 10, 4 -> 5, 5 -> any fire at all);
    impact never fires (oil = 4: ignites at 5 fire damage)
  - 6-10 explosive: any spark fires ignite; a single blunt hit of
    100 - 20*(vol-5) fires impact (black potion = 9: 20+ blunt)
  - explode's force defaults to volatility * source.Weight() when not
    authored (a full cask of black potion is a siege weapon; a half-drunk
    dose is a weak grenade); explode's signature is (dmgtype="f",
    amount=None) so the common type-only override reads ("explode","t")
- Doses: DOSE_WEIGHT = 4 (one driblet, one gulp). One dose gives the full
  effect; no dose scaling of effect strength. Exceptional stackable potions are
  a layer on top, not part of the base system. Round down always; lossy
  remainders; sub-dose fluid does nothing when drunk. Fills quantize to whole
  doses at the bottle boundary (all-or-nothing below one dose).
- Bottle geometry: Box.Size() = weight (hollow-vessel rule, ignores density).
  Bottle capacity defaults to 2*Size() when None (bottles hold more liquid than
  their size suggests). neckSize defaults to Size(); solids must fit through
  neckSize, plashes are exempt. Standard 4wt bottle: size 4, capacity 8, 2 doses.
- Cork: Bottle.open() from inside the bottle requires an ATHL contest vs 20.
  Box.enter/exit unconditionally clear closed; Bottle must override so corking
  a captured creature works. Auto-open on outside-entry is fine. Sealed bottles
  resist contamination/spills and hide scent; glass transparency still reveals
  color and visible contents (no hidden status through transparent compositions).
- dominantFluid comparator: max by (Size, density, -id). Shared by three
  consumers: Bottle.requiredImmersion (returns a fluid whenever one exists; no
  dry ledge inside a bottle), imbibe delegation, and vessel naming. Multiple
  fluids may coexist in a vessel (e.g. oil refusing to mix with water).
- Naming is computed, never stored: "an empty bottle" when empty, otherwise
  named by the dominant fluid ("a green potion", "a bottle of oil"). A drop of
  oil in a green potion does not rename it; drinking all the green potion does
  (dominance passes to the oil). examine reveals full contents through glass.
- Contained plashes are mention=False (the vessel speaks for its contents);
  mention is restored when a plash exits to a Room. Handle both at the
  Room.add / Container.add chokepoints, where timeDespawn/nullDespawn live.
- Spill lifetime (implemented): a finite Plash landing in a Room arms
  despawnTimer = weight (grace period), then drains 1 per passTime call.
  Infinite Plashes assert against having a despawnTimer. Contained plashes
  never decay (Container.add calls nullDespawn).
- Mixing: deferred to Phase 3. For now two liquids in one vessel coexist and
  merge() returns False. Later: mixCompositions(a,b) + recipe lookup; default
  result is murk (useless); contamination is total (no dilution model); this
  rule is the potion economy's load-bearing wall (kills pond-buffing and
  dose-dilution exploits). Bottles force-merge plashes inside them.

SHARED DESIGN PRINCIPLES
===============================================================================

- Separate containment from tethers and statuses.
- Give every mutable relationship one authoritative source.
- Derive reverse collections when the search scope is local and well-defined.
- Centralize multi-step relationship mutations in one API.
- Snapshot derived reverse relationships before temporarily detaching an object.
- Separate planning/validation from mutation.
- Do not use gameplay mutation APIs during world construction.
- Normalize first, resolve second, validate last.
- Use explicit special cases where physics genuinely differ instead of forcing one
  overloaded method to answer several unrelated questions.
- Keep source-maintained statuses synchronized from authoritative relationships rather
  than treating persisted status entries as the source of truth.
